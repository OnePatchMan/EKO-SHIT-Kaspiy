# Как дообучить модель после первого рабочего сценария

В текущей версии используются готовые официальные веса YAMNet. Свои веса ещё не обучены. Дообучение имеет смысл после проверки данных и исходного качества; оно не гарантирует улучшения.

## Аудиоданные

Для каждой независимой исходной записи сохранить: файл, source_url, author, license, original_id, место и время при наличии, тип микрофона, условия записи, метки и group_id. Фрагменты и аугментации одной записи имеют общий group_id. Примеры из текущего пакета — небольшие демонстрационные controls, а не готовая обучающая выборка. Надводные записи нельзя считать проверкой гидрофонов.

Целевые метки: лодка, выстрел. Дополнительные отрицательные / фоновые данные: вода, ветер, птицы, речь, автомобильный двигатель, гром, фейерверк, хлопок. Если лодка звучит вместе с водой или выстрелом, допустимы несколько одновременных меток. Общее слово Engine само по себе не является достоверной разметкой лодки. Синтезированные выстрелы помечать отдельно от полевых записей.

Разделить исходные группы на train, validation, test **до нарезки окон**. По возможности разделять по сессии, месту, устройству и автору. Несколько независимых записей дают больше информации о переносимости, чем тысячи окон одной записи. Проверить пересечение с предварительным обучением YAMNet; если оно неизвестно, не называть тест полностью независимым от исходного AudioSet.

## Обучение

1. Для каждого WAV повторить то же преобразование, что в сервисе: mono float32, 16 кГц.
2. Применить фиксированную YAMNet, получить embeddings формы N×1024.
3. Обучить небольшой выходной классификатор над embeddings. Для нескольких меток использовать независимые выходы; не заставлять фон и лодку исключать друг друга.
4. Весь подбор архитектуры, регуляризации, порогов и правила объединения окон выполнять на train/validation. Сохранить конфигурацию и случайные seed.
5. Один раз оценить окончательный вариант на test и сравнить с исходной YAMNet на той же разметке.
6. Отчёт: число исходных файлов по классам и группам; precision и recall лодки/выстрела; ложные предупреждения на час размеченного фонового аудио; ошибки по микрофонам и шумам; измеренная задержка на CPU.
7. Сохранить обученные веса, словарь меток, preprocessing, пороги, версии и результаты. После замены модели повторить HTTP проверки. Эндпоинт Java менять не требуется, но model_version должен измениться.

Официальная инструкция извлечения embeddings, обучения и экспорта: https://www.tensorflow.org/tutorials/audio/transfer_learning_audio . Текущий исходный YAMNet использует Keras 2 / tf-keras; пример из старого ноутбука нельзя механически копировать с несовместимым Keras 3. Фиксировать работающие версии.

## Прогноз реального нереста

Нужны сопоставленные по участку, виду и времени измерения воды и наблюдения фактического нереста за несколько сезонов, включая сведения об усилии наблюдения. «Наблюдения отсутствуют» и «нерест отсутствует при достаточном наблюдении» — разные состояния.

Заранее определить цель: например, наблюдалось ли начало нереста выбранного вида в участке в следующие 72 часа. Признаки строить только из данных, доступных на issued_at: температура и её динамика, уровень и его динамика, обводнение, сезон и остальные реально измеряемые показатели. Будущие измерения не должны попадать в признаки.

Проверять на более поздних сезонах и, при достаточных данных, на других участках; сравнить с простым сезонным и гидрологическим правилом. Для табличных данных сначала сравнить простую статистическую модель и градиентный бустинг, затем решать, нужна ли временная нейросеть. Вид алгоритма выбирается по результатам, а не по слову «нейросеть» в презентации.

До этой проверки текущий сценарный результат не становится вероятностью нереста. Нельзя генерировать метки по своему же температурному правилу, обучить модель воспроизводить их и считать это доказанной биологической точностью.
